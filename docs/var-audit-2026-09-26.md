## 性能

订单按买卖方向只排序一次，TP 覆盖量和批次集合使用一次遍历，去掉多个批次数乘订单数的循环。Windows 原生 Python 3.11、每个场景 100 次、相同无新成交输入的单次计算中位数：

| 批数 | 修改前 | 修改后 |
| --- | --- | --- |
| 3 | 0.062 ms | 0.063 ms |
| 30 | 0.366 ms | 0.282 ms |
| 200 | 5.829 ms | 1.626 ms |

可运行 `python scripts/benchmark_qqq_scalper.py` 复测当前实现。这是合成 CPU 测量，不能换算为真实下单延迟或收益。

QQQ 历史采用同一个 SQLite 读事务中的计数与流式读取，只保留每桶端点和各账户极值，输出仍不超过 900 点；新压缩记录只把绘图字段送入 Python。兼容旧压缩记录需要解压以核实账户名，不能为了速度猜测账户顺序。`scripts/benchmark_qqq_history.py` 在临时数据库复测时间和 Python 峰值内存。读取总工作量仍随窗口记录数增长，账本不因本次优化删除历史。

同一 Windows 环境、3 账户、3 次运行的中位数如下；新格式场景包含 10% 未压缩旧记录，内存为 `tracemalloc` 测到的 Python 峰值，不含 SQLite 原生缓存：

| 历史场景 | 修改前耗时 / 峰值内存 | 修改后耗时 / 峰值内存 |
| --- | --- | --- |
| 50,000 条、4 KiB 状态 | 0.620 s / 35.32 MiB | 0.653 s / 0.526 MiB |
| 150,000 条、1 KiB 状态 | 1.452 s / 105.75 MiB | 1.706 s / 0.519 MiB |
| 20,000 条无账户名旧压缩记录 | 0.159 s / 14.16 MiB | 0.461 s / 0.566 MiB |

历史优化降低峰值内存，不承诺读取更快；旧压缩记录因必须核实账户名而更慢。以上场景抽样结果相同，另外用回归测试验证账户重排与缺值时的新正确行为。

## 安全边界与接入条件

现有两个 HTTP 客户端仍只允许固定行情/会话端点，无订单、提款或转账路径。`vr-token` 只送固定 Variational HTTPS 源，不随重定向外发；Lighter 不携带 Var 会话。新执行基础与 paper 账本分离，见 [执行准备与离线演练](execution-readiness.md)。

网页默认只绑定 loopback，随机页面 token 负责跨站请求防护，不是本机进程身份认证。Linux 网页与模拟 writer 共用服务 UID 和 state 写权限。未来带交易能力的会话需要独立执行服务及明确访问权限，不能直接给现有监控进程增加任意写接口。工作台代理的关联入口另作只读抽查：`project_aggregation/server/app.mjs` 要求登录后取得项目入口，`server/portal.mjs` 先校验项目授权再重写 upstream Host/Origin；这不是对实际服务器部署或整个工作台的新一轮安全认证。

本轮只确认现有 `vr-token` 鉴权报价实现。公开 API 文档不代表前端会话交易协议；公开网页资源读取返回 403，尚未取得可验证的下单/接受 firm quote、远端幂等查询、订单/成交/持仓、保证金和限流协议证据。不能推测请求路径，不能把 indicative 报价当作可接受成交承诺。真实资金预算、最大单腿敞口和持有时长仍需显式设置，不能继承 paper 的无限保证金选项。
